# commit: 변경사항 분석 → 단위 분류 → 메시지 작성 → 커밋

변경사항을 읽고 커밋 계획을 세운 뒤 **승인을 따로 묻지 않고 바로 커밋**한다. 커밋 요청 자체가 승인이다. 대신 아래 "중단 조건"에 해당하면 멈추고 사용자에게 묻는다.

## Step 0: 저장소 지침 확인

저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 규칙이 있으면 이 스킬보다 우선한다. 사용자 전역 설정(`~/.claude/CLAUDE.md`)의 커밋 규칙도 그대로 따른다.

## Step 1: 변경사항 파악

아래를 실행해 상태를 파악한다.

```bash
git status --short
git diff --stat
git diff              # unstaged
git diff --staged     # 이미 staged 된 것
git log --oneline -10 # 기존 메시지 스타일 확인 (커밋이 없으면 생략)
```

- untracked 파일은 `git diff`에 나오지 않으므로 `git status`에서 목록을 보고 필요한 것만 내용을 읽는다.
- diff가 크면 `--stat`으로 윤곽을 잡고 파일별로 나눠 읽는다.
- 변경이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- **커밋하면 안 되는 파일**을 걸러낸다: `.env`, 키·토큰·비밀번호가 담긴 파일, `node_modules`, `dist`, 빌드 산출물, 로그. 의심되면 커밋 계획에서 빼고 사용자에게 알린다. 이미 staged 된 파일 중 해당하는 것이 있어도 마찬가지다.
- 파일 내용에서 비밀값을 발견하면 값을 출력하지 말고 파일명과 행 번호만 알린다.

## Step 2: 논리적 단위로 분류

하나의 커밋은 **하나의 이유**로 설명되어야 한다. 아래 기준으로 묶는다.

- 같은 목적의 변경(기능 하나, 버그 하나, 리팩터링 하나)은 한 커밋.
- 서로 다른 종류(기능 추가 + 포맷 정리 + 설정 변경)는 분리.
- 한 파일 안에 성격이 다른 변경이 섞여 있으면 hunk 단위 분리가 필요한지 판단한다. 분리 비용이 크면 한 커밋으로 묶되 그 사실을 계획에 적는다.
- 의존 순서를 고려한다. 앞 커밋 없이는 빌드가 깨지는 구성이면 순서를 정하거나 합친다.

분리하는 이유: 나중에 `git revert`, `git bisect`, 리뷰가 쉬워지고 history가 "무엇을 왜 바꿨는지"를 말해 준다.

## Step 3: 커밋 메시지 작성

형식: `type: 한국어 요약.`

| type | 용도 |
|---|---|
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·기타 잡무 |
| docs | 문서 |
| test | 테스트 추가·수정 |
| style | 포맷·공백 등 로직 무관 변경 |

규칙:

- **한 줄, 한국어, 마침표로 끝낸다.** 예: `feat: 컴포넌트 생성 폼 추가.`, `fix: 빈 props 입력 시 파싱 오류 수정.`
- 요약은 "무엇을 했는지"를 구체적으로. "수정", "업데이트"처럼 내용 없는 표현은 피한다.
- 저장소의 기존 `git log` 스타일이 있으면 그 톤을 맞춘다.
- 본문이 꼭 필요한 큰 변경이 아니면 제목 한 줄만 쓴다.
- **`Co-Authored-By` 트레일러와 "Generated with Claude" 류 문구는 붙이지 않는다.** 사용자 전역 설정이 금지하고 있고, 사용자 지침이 기본 동작보다 우선한다.

## Step 4: 계획 요약 (승인 대기 없음)

커밋하기 전에 계획을 짧게 출력하고 곧바로 Step 5로 넘어간다. 사용자가 무엇이 커밋되는지 알 수 있게 하는 용도이며 응답을 기다리지 않는다.

```
커밋 계획 (2개)
1. feat: 컴포넌트 생성 폼 추가. — src/components/GeneratorForm.tsx, src/App.tsx
2. chore: eslint 설정 갱신. — eslint.config.js
제외: .env.example (사유: ...)
```

### 중단 조건 — 이 경우에만 커밋 전에 사용자에게 묻는다

승인을 생략하는 대신, 되돌리기 어려운 실수가 될 만한 상황에서는 멈춘다.

- 비밀값(키·토큰·비밀번호 등)이 들어 있을 가능성이 있는 파일이 변경에 포함된 경우 (해당 파일은 빼고 나머지만 커밋할지 묻는다)
- 어떤 파일을 커밋해야 할지 판단 근거가 없는 경우 (예: 사용자가 말한 작업과 무관해 보이는 대량 변경)
- 이미 staged 된 파일 구성이 사용자가 의도적으로 고른 것으로 보이는 경우 (그대로 그 구성만 커밋할지 확인)

## Step 5: 커밋 실행

계획을 순서대로 실행한다.

1. **명시적 경로만 staging** 한다: `git add <파일1> <파일2>`. `git add .`, `git add -A`, `git add -u`는 쓰지 않는다 — 무관한 파일이 섞여 들어가는 사고를 막기 위해서다.
2. 이미 staged 된 파일 중 이번 커밋에 속하지 않는 것이 있으면 `git restore --staged <경로>`로 내린다.
3. `git commit -m "<메시지>"` 로 커밋한다.
4. **커밋 직후 `git show --stat HEAD`로 의도한 파일만 들어갔는지 확인**한다. 다르면 사용자에게 보고한다.
5. 다음 커밋으로 넘어가기 전에 `git status --short`로 남은 변경을 확인한다.

금지:

- `--amend`, `reset`으로 history 다시 쓰기. 잘못된 커밋은 새 커밋으로 고친다.
- `--no-verify`로 훅 우회. pre-commit 훅이 실패하면 원인을 고치고 **새로** 커밋한다(실패한 커밋은 만들어지지 않았으므로 amend 대상도 없다).
- `git push`. 사용자가 요청하지 않았다면 하지 않는다.

## Step 6: 결과 보고

커밋 해시와 메시지를 목록으로 보고하고, 남은 변경(제외한 파일 등)이 있으면 함께 알린다.

```
완료: 2개 커밋
- a1b2c3d feat: 컴포넌트 생성 폼 추가.
- e4f5g6h chore: eslint 설정 갱신.
남은 변경: .env.example (제외)
```

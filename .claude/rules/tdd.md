# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.

## 적용 기준

**TDD 필수**

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트가 먼저)

**TDD 불필요**

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업·스타일)
- SQL

경계가 모호하면 **적용 쪽**으로 판단한다. 로직(분기, 상태, 변환)이 하나라도 있으면 순수 UI가 아니다.

## RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 문법 오류, import 실패, 오타로 인한 실패는 RED가 아니다. 고쳐서 올바른 이유로 실패하게 만든다.
- 실패 메시지를 확인하고 기록한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI** — 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 + 기존 테스트 모두 통과**를 확인한다. 신규만 돌리고 끝내지 않는다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 변경할 때마다 테스트를 실행한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 다음 RED로 간다.

### 반복

- 다음 동작이 남아 있으면 **RED로 돌아간다.** 한 사이클이 끝나기 전에 다음 동작을 구현하지 않는다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 보면서 다시 쓰면 테스트가 코드를 따라가게 된다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 먼저 깨지고, 테스트도 30초면 쓴다. 단순하면 테스트 비용이 더 낮다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 보고 쓰므로 **이미 통과하는 테스트**가 된다. 결함을 못 잡는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. 테스트 없이 얻는 속도는 빌린 시간이다. |
| "삭제하면 낭비" | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 TDD 불필요 대상에 해당하는지 먼저 따진다. 해당하지 않으면 적용한다. |
